1 整体架构总览

本系统以 项目 为载体，以 应收单 为业财桥梁， 形成一条从发货到收款的完整单据链：发货 → 应收确认 → 开票 → 收款 → 核销。 审批流由 Flowable 工作流引擎驱动，最终通过看板汇总展示。

核心设计升级： 从"三条线独立并行"升级为"单据链模式"。 应收单是业务和财务的桥梁——发货确认后生成应收单， 开票基于应收单下推，收款和应收单核销形成闭环。 所有金额以应收单为基准，不再是项目维度简单累加。

2 核心业务实体

系统共包含 23个核心实体（15个业务实体 + 8个系统实体），以"应收单"为业财桥梁形成单据链。 审批流由 Flowable 引擎管理（ACT_* 表），权限系统采用标准 RBAC 模型，字典管理采用类型+数据双表方案。 所有涉及红字冲减的实体均支持负数单据方向（蓝字/红字）。

3 工作流引擎架构
3.1 选型决策：Flowable

由于审批需求涉及 驳回到任意节点、逐级+自定义混用、角色+具体人双模式、 审批人动态调整等全高复杂度功能，手写状态机已无法满足可维护性要求， 决定引入 Flowable 工作流引擎作为审批流的核心驱动。

🏆 为什么选 Flowable
  • 遵循 BPMN 2.0 国际标准，流程定义可移植
  • 中文社区活跃，学习资料丰富
  • 轻量嵌入，不臃肿，适合中小项目
  • 支持驳回、跳转、动态节点、多实例
  • 历史记录/审计由引擎自动管理
⚙ 引擎核心能力
  • 流程定义（BPMN XML / 可视化设计器）
  • 流程实例生命周期管理
  • 用户任务分配与领取
  • 驳回 / 跳转 / 撤回
  • 历史数据自动记录（ACT_HI_* 表）
  • 任务监听器 / 执行监听器
📊 与业务系统集成方式
  • 项目表保存业务数据 + 流程实例ID
  • 审批节点配置由管理员在后台维护
  • 审批动作通过 Flowable API 触发
  • 审批状态从引擎查询，不冗余存储
  • 审批通过/驳回回调更新业务状态
3.2 Flowable 核心表说明

Flowable 自带一套表结构（ACT_ 开头），覆盖运行时、历史、模型、身份等。 本系统重点使用以下几类表，无需自己设计审批记录表：

表名 类别 作用
ACT_RE_PROCDEF 流程定义 已部署的流程定义（"项目立项审批"这个流程本身）
ACT_RU_EXECUTION 运行时 流程实例执行记录（某个项目正在走的审批流）
ACT_RU_TASK 运行时 当前待办任务（当前卡在哪个审批节点）
ACT_RU_IDENTITYLINK 运行时 任务与用户/角色的关联关系（谁审批这一步）
ACT_HI_PROCINST 历史 流程实例历史（每个项目的审批全程记录）
ACT_HI_TASKINST 历史 任务历史（每个审批节点的处理记录）
ACT_HI_COMMENT 历史 审批意见 / 驳回原因记录
ACT_HI_ACTINST 历史 活动实例历史（流程每一步流转轨迹）
设计原则： 审批数据完全交给 Flowable 管理，业务表只存 processInstanceId（流程实例ID） 做关联。需要审批记录时从引擎查，不做双写，避免数据不一致。
3.3 流程定义的配置方式

审批节点不写死在代码里，由管理员在系统后台配置。配置内容包括：

📋 节点配置
  • 节点名称（如"部门主管审批"）
  • 节点类型：逐级 / 指定人 / 指定角色
  • 审批人（用户ID 或 角色编码）
  • 节点顺序
  • 是否可驳回
⚡ 动态生成
  • 管理员保存配置后
  • 系统动态生成 BPMN XML
  • 部署到 Flowable 引擎
  • 生成新版本流程定义
  • 已有流程实例不受影响
🔄 版本管理
  • 流程定义支持多版本
  • 新发起的流程用最新版本
  • 已在途的流程按旧版本走
  • 管理员可查看历史版本
4 项目立项审批流程
4.1 五大高复杂度决策

审批流全部按最高复杂度实现，以下是五大设计决策的最终结论：

决策点 选择 说明
驳回后已审批意见处理 保留且复用 之前已同意的节点跳过不用再审，驳回节点及之后的节点重新走
重新提交后从哪开始 从驳回处续走 不从头走全流程，从被驳回的那个节点继续往下流转
逐级 + 自定义审批人 可混用 某几级走逐级（按组织架构），某几级指定具体人员，可交替配置
审批人绑定方式 角色 + 具体人 每个节点可选择绑定具体用户，或绑定角色（自动解析到用户）
审批人离职/调岗 自动按角色重新分配 角色绑定的节点自动找新的岗位持有人；指定人的节点需管理员转交

4.3 审批动作详解
✅ 同意
  • 当前审批人点击"同意"
  • 流转到下一个审批节点
  • 最后一级同意 → 流程结束 → 项目建档
  • 审批意见存入 ACT_HI_COMMENT
❌ 驳回
  • 可选择驳回到哪个节点
  • 选项：发起人 / 任意已审批节点
  • 必须填写驳回原因
  • 驳回节点之前的已审批记录保留
  • 驳回节点及之后的任务被取消
🔄 重新提交
  • 发起人修改内容后重新提交
  • 从被驳回的节点继续往下走
  • 驳回节点之前已同意的跳过
  • 驳回节点重新生成任务
  • 驳回节点之后重新依次流转
4.4 驳回跳转规则（核心逻辑）
场景举例： 流程：发起人 → 节点A(已同意) → 节点B(已同意) → 节点C(当前审批人) → 节点D → 节点E → 通过
如果节点C驳回到节点A，重新提交后：节点A 重新审 → 节点B 重新审 → 节点C 重新审 → 节点D → 节点E → 通过
规则：驳回到节点X，则 X 及之后的所有节点全部重走，X 之前的跳过。
驳回目标 重新提交后起点 已审批节点处理
驳回到发起人 从第1个审批节点开始 所有审批节点全部重走
驳回到第 N 个已审批节点 从第 N 个节点继续 第 1 ~ N-1 个节点跳过，第 N 个及之后重走
驳回到当前节点的上一级 从上一级节点继续 上一级之前的跳过，上一级及之后重走
4.5 审批人解析规则

每个审批节点配置时，可以选择以下三种方式之一来确定审批人：

类型 配置方式 运行时解析
指定人 选择具体的用户ID 直接分配给该用户
指定角色 选择角色编码（如"部门主管"） 通过角色解析器找到对应用户，分配任务
逐级（上级） 选择"按组织架构逐级" 根据发起人的组织架构，自动找直属上级、上级的上级...
角色解析器： 系统实现一个 IdentityResolver 组件，负责把"角色编码"或"逐级"解析成具体的用户ID。 当人员调岗时，只需更新组织架构/角色绑定，新发起的流程自动生效。 在途流程中未到达的节点按最新架构解析，已完成的节点不受影响。

5.1 流程说明

发货流程以 发货批次 为单位，一个项目可以分多批发货。 每批走完"申请 → 发货 → 客户验收收货"后，系统按已收货数量自动生成应收单。 支持部分收货：客户可以逐行确认收货数量，已收部分生成应收，未收部分可发起退货。

📦 分批规则
  • 每批发货需关联具体的货物明细行
  • 同一货物明细可分多次发出
  • 每批发货数量 ≤ 该货物剩余未发数量
  • 批次号自动生成：FH-项目编号-001
  • 每批发货对应一张应收单
📈 金额计算
  • 每批发货金额 = 该批数量 × 单价

  • 发货金额不得超过合同总金额

  • 退货流程（三级审批 + 冲减）
  • 红字应收单（负数冲减）
⚠ 暂不支持

  • 暂估应收（按收货确认即应收）
  • 换货（需走两次退货流程）

6 应收单管理
6.1 什么是应收单

应收单是业务和财务的桥梁——业务侧确认"货发出去了"， 财务侧就确认"客户欠我们钱了"。它是开票的依据，也是收款核销的对象。 简单说：应收单就是"客户欠我们多少钱"的正式账单。

📦 来源（怎么来的）
  • 发货确认收货后自动生成（主要来源）
  • 一张发货单对应一张应收单
  • 金额从发货单带过来，不改
  • 应收日期 = 客户确认收货日期
📝 去向（用来干嘛）
  • 作为开票的依据（下推生成发票）
  • 作为收款核销的对象
  • 计算应收余额和账龄
  • 财务确认收入的依据
📈 三个核心金额
  • 应收金额：总共该收多少钱
  • 已核销金额：已经收回来多少
  • 未核销金额：还欠多少 = 应收 - 已核销
  • 每次核销后自动更新这三个数

设计简化： V1版本应收单在发货确认收货后自动生成并直接生效， 不需要单独的审批流程。这是因为发货本身已经经过销售和主管发货人员确认， 应收单只是财务侧的"影子记录"。如果以后需要财务审核应收，再加审批节点。

7 开票流程
7.1 流程说明

开票以 应收单 为依据——销售经理在应收单列表中选择待开票的应收单， 下推生成开票申请。开票员开具发票后上传系统并批准，销售人员下载发票发给客户。 一张应收单可以开多张发票（分批开票），但开票总金额不能超过应收单金额。

核心变化： 之前是"对着项目开票"，现在是"对着应收单开票"。 有了应收单这个锚点，开票就有了依据——不能凭空开票，必须对应到具体哪批发货的应收。 这样财务数据才能追溯：发票 → 应收单 → 发货单 → 销售订单。

📝 开票来源
  • 必须基于应收单下推
  • 一张应收单可开多张发票（分批开）
  • 开票金额 ≤ 应收单未开票金额
  • 支持多张应收单合并开票
💾 发票与应收关联

✅ 已支持

  • 基于应收单下推开票
⚠ 暂不支持
  • 发票作废（独立于退货的场景）
  • 电子发票自动开具
  • 发票拆分（一张应收拆成多张票）
  • 开票审批流程

8 回款流程（收款单）
8.1 流程说明

客户付款后，由 销售经理 在项目上提交收款申请，上传银行回单作为凭证。 出纳 审批通过后，生成正式的收款单。 收款单生效后，需要与应收单进行核销，明确这笔钱收的是哪笔应收的款。

核心变化： 从"回款直接加到项目金额"升级为"收款单 + 核销"模式。 收款单只是"钱到了"的记录，核销才是"这笔钱对应哪笔应收"的匹配。 没有核销的收款只是"预收/待核销"状态，不计入已回款统计。

💰 收款金额
  • 客户实际付了多少钱
  • 由出纳审批确认
  • 审批后不可修改
🔁 已核销金额
  • 已经匹配到应收单的金额
  • 每次核销后累加
  • ≤ 收款金额
⌛ 未核销金额
  • 还没匹配的金额
  • = 收款金额 - 已核销金额
  • 全部核销后为 0

9 核销机制
9.1 什么是核销

核销就是把"收款单"和"应收单"对上号——明确这笔钱收的是哪笔应收的款。 没有核销的话，你只知道"客户总共欠了100万，总共付了80万"， 但不知道"这80万是付的哪几批货的钱，还欠的20万是哪批发货的"。

打个比方： 应收单就像餐厅的"账单"，收款单就像客人付的"钱"。 核销就是服务员把钱和账单对应上——"这桌客人付了500，正好是他们那桌的账单"。 没核销就像"收了一堆钱，但不知道哪笔钱对应哪桌的饭钱"。
9.2 核销方式
🟠 自动核销
  • 按"时间最早优先"自动匹配
  • 同一客户的收款和应收自动对
  • 适合：收款金额正好等于某笔应收
  • 出纳点一下"自动核销"按钮
🟡 手工核销
  • 出纳手动选择哪笔收款对哪笔应收
  • 可以一对多、多对一、多对多
  • 适合：部分收款、抹零、合并付款
  • 灵活但需要人工判断
📝 核销记录
  • 每次核销生成一条核销记录
  • 记录：应收单ID + 收款单ID + 核销金额
  • 核销后不可删除，只能反核销
  • 完整保留核销轨迹
9.3 核销规则
规则 要求 说明
同一客户 必须 收款单和应收单必须是同一个项目（同一个客户）
核销金额 ≤ 应收未核销 必须 不能核的比应收还多
核销金额 ≤ 收款未核销 必须 不能核的比收款还多
部分核销 支持 一笔应收可以分多次收款核销
一笔收款核多笔应收 支持 客户一次付了好几批货的钱
反核销 支持 核销错了可以撤销，恢复原状

事务一致性： 核销是一个事务操作——必须同时更新收款单的已核销金额和应收单的已核销金额， 并且插入核销记录。三者必须同时成功或同时回滚， 绝对不能出现"收款单核了但应收单没核"的不一致状态。
10 退货流程
10.1 前提条件

退货的前提是货物已发出且客户已收到货（发货状态为"部分收货"或"全部收货"）。 不能对未发货或未收货的货物发起退货。 退货由销售人员发起，经过三级审批后，系统自动执行后续冲减动作。

业务方描述： "退回审批，得先收到货物，也就是说发起退货审批先由上级审批，然后财务审批， 再然后到主管业务人员，审批完成后后边跟着的是待办：负数冲发票、负数冲收入、收款退回。"

审批通过 系统自动 执行冲减待办 执行中 自动执行三个冲减动作（见10.4）
执行中 系统自动 冲减完成 已完成 所有冲减动作执行完毕
审批引擎： 退货审批同样走 Flowable 工作流引擎，流程定义独立配置。 三级审批为固定线性流程（上级→财务→主管），驳回一律退回发起人重新提交。 这比立项审批简单，不需要驳回到中间节点。
10.4 审批通过后的三个冲减待办

审批通过后，系统自动按顺序执行以下三个冲减动作，每个动作都是一条待办任务：

① 负数冲应收
  • 生成红字应收单（负数金额）
  • 关联原蓝字应收单
  • 金额 = 退货数量 × 单价（负数）
  • 原应收单的应收金额自动冲减
  • 如果原应收已核销，生成退款待核销
② 负数冲发票
  • 前提：原应收单已开过发票
  • 生成红字发票（负数金额）
  • 关联原蓝字发票
  • 原发票的已开票金额冲减
  • 如果未开过票，跳过此步
③ 收款退回
  • 前提：原应收已收过款
  • 生成退款收款单（负数金额）
  • 自动反核销原核销记录
  • 恢复原应收单的未核销金额
  • 如果未收过款，跳过此步
执行顺序： 三个冲减动作按顺序执行：先冲应收 → 再冲发票 → 最后处理退款。 每个动作独立执行，前一个失败不影响后一个（但要记录异常）。 如果某个动作的前提不满足（如未开票），自动跳过。
10.5 退货场景示例
完整场景：
1. 项目发货100台设备，单价1万，合同总金额100万
2. 客户收货80台，20台有问题 → 发货状态为"部分收货"
3. 系统按80台生成应收单，应收金额 = 80万
4. 销售对20台发起退货申请（退货金额 = 20万）
5. 上级审批 → 财务审批 → 主管审批 → 通过
6. 系统自动执行：
    ① 如果20台未计入应收（部分收货场景）→ 冲减发货数量，无需冲应收
    ② 如果20台已计入应收 → 生成红字应收单 -20万，原应收单冲减
    ③ 如果已开票 → 生成红字发票 -20万
    ④ 如果已收款 → 生成退款单 -20万，反核销原记录
7. 退货完成，项目应收金额 = 80万，已开票/已收款相应调整
10.6 退货对各单据的影响
单据 冲减方式 说明
发货单 退货数量冲减已发数量 发货明细行的已发数量减少退货数量
应收单 生成红字应收单（负数） 关联原应收单，冲减应收金额
销售发票 生成红字发票（负数） 关联原发票，冲减已开票金额（如已开票）
收款单 生成退款单（负数） 反核销原核销记录，恢复应收未核销金额（如已收款）
核销记录 反核销 原核销记录标记为"已反核销"，生成反向核销记录
11 单据链依赖关系

升级为"应收单 + 核销"模式后，三条线不再是完全独立并行， 而是形成了一条有依赖关系的单据链。 核心锚点是应收单——发货生成应收，开票基于应收，收款核销应收。

单据链全景图
发货单
➞
应收单
➞
销售发票
收款单
⇅
核销
⇅
应收单
发货 → 应收（强依赖） ｜ 应收 → 开票（强依赖） ｜ 收款 ↔ 应收（核销匹配）
各单据之间的依赖关系
关系 依赖类型 说明
发货单 → 应收单 强依赖 确认收货后自动生成应收单，一张发货单对应一张应收单
应收单 → 销售发票 强依赖 开票必须基于应收单下推，不能凭空开票
收款单 → 应收单 核销依赖 收款单可独立存在（预收款），但核销必须有应收单
发货金额 ≤ 合同总金额 金额上限 发出的货物总价值不能超过合同总金额
开票金额 ≤ 应收金额 金额上限 开票金额不能超过应收单的未开票金额
核销金额 ≤ 应收/收款 金额上限 每次核销金额不能超过双方的未核销金额
开票 vs 收款 无依赖 可以先开票后收款，也可以先收款后开票
设计原则： 有依赖的地方严格控制（应收必须有发货、开票必须有应收）， 没有依赖的地方保持灵活（开票和收款谁先谁后不限制）。 这样既保证了财务数据的可追溯性，又不限制业务的实际操作节奏。

12.1 RBAC 架构

系统采用标准 RBAC（Role-Based Access Control）模型，用户-角色-权限三层解耦。 管理员通过后台界面配置角色和权限，无需修改代码。

权限链路： User → UserRole → Role → RolePermission → Permission → Menu
校验时机： 后端拦截器统一校验（安全边界），前端按 Menu 动态渲染（体验优化）
12.2 数据范围策略 DataScope

每个角色配置一个数据范围策略，控制用户能看到哪些数据范围的数据。

12.3 互斥角色约束 RoleConflict

职责分离原则：以下角色对不能同时分配给同一个用户，防止"自己审批自己"的风险。

角色A 角色B 互斥原因
销售经理 出纳 销售经理提交回款申请，出纳审批——同一人会导致自己提交自己审批
开票员 出纳 开票和收款是两个独立的财务动作，同一人操作存在资金风险
销售人员 出纳 销售负责业务端，出纳负责资金端，职责必须分离
销售经理 开票员 销售经理提交开票申请，开票员开具——同一人可自己申请自己开票
RBAC 红线： 权限校验必须在后端拦截器统一执行，前端隐藏按钮只是体验优化，不是安全边界。 互斥角色约束在分配角色时由后端强制校验，违反则拒绝分配。 角色继承不超过3层，防止权限传递过度膨胀。

14 数据删除策略
核心原则： 财务系统不删除，只冲销。一笔业务发生后永远不能从数据库消失， 错了用红字单据冲减，不用删除。删除策略按实体类型分层处理。
14.1 分层策略
层级 适用实体 策略 原因
第一层 应收单、收款单、发票、核销记录、退货记录 不可删除，只能红冲 财务凭证，审计合规要求永久保留。错了生成红字单据冲减原单
第二层 项目、发货记录、发货明细行、货物明细 逻辑删除 业务数据，可能被其他单据引用。物理删除会导致引用断裂
第三层 角色、权限、菜单、组织架构、用户、流程定义 停用代替删除 系统配置，停用后不可引用但保留历史关联
第四层 未提交的草稿申请、临时文件、文件下载记录 可物理删除 无业务价值的临时数据，定期清理
第五层 审计日志 只增不删不改 审计底线，法律合规要求
14.2 红冲示例

应收单生成了10万，后来发现应该是8万：

蓝字应收单 +10万
→
红字应收单 -10万（冲销原单）
→
新蓝字应收单 +8万

审计链路完整保留：+10万 → -10万 → +8万，每一步都可追溯。

14.3 技术实现
🔒 逻辑删除字段
  • is_deleted boolean 默认false
  • deleted_at datetime 记录删除时间
  • deleted_by bigint 记录删除人
  • ORM拦截器统一追加 WHERE is_deleted = false
⚠ 停用校验
  • 停用时校验是否被引用
  • 被引用的不能直接停用（或提示影响范围）
  • 已停用的不能被新业务引用
💾 草稿清理
  • 定时任务清理超过30天的未提交草稿
  • 清理无引用的临时文件
  • 文件下载记录保留90天后清理
删除红线： 第一层实体绝对不能提供删除接口，只能走红冲流程。 第二层实体逻辑删除后不可恢复（管理员也不行），如需恢复则新建。 第五层审计日志只增不删不改，任何角色都没有删除权限。
15 初始化安装与系统重置
设计原则： 系统交付时通过安装向导完成初始化；试运行期间支持数据重置； 上线后重置功能永久禁用，通过 SysConfig 的 trial_mode 控制。
15.1 初始化安装向导

类似 WordPress 安装流程，通过浏览器引导式完成，不走命令行。首次访问系统时检测 sys_initialized 标记，未初始化则跳转安装向导。

步骤 操作 说明
1 环境检查 检测数据库连通性、Flowable 表是否存在、文件存储目录可写、磁盘空间充足
2 初始化数据库 执行建表 DDL（业务表 23 张 + Flowable ACT_* 表），幂等设计可重复执行
3 写入种子数据 角色、权限、菜单、字典类型/数据、互斥角色配置、组织架构（默认根节点）
4 初始化管理员 创建超管账号，设置初始密码，标记 force_change_password = true（首次登录强制改密）
5 部署流程定义 将 BPMN 文件部署到 Flowable 引擎，审批流可用
6 写入完成标记 SysConfig 写入 sys_initialized = true、trial_mode = true，防止重复初始化
15.2 系统重置策略

重置功能仅在 试运行模式（trial_mode = true）下可用，上线后接口直接返回 403。

维度 轻度重置 完整重置 适用场景
清理范围 业务数据表：项目、货物明细、发货记录/明细行、应收单、收款单、发票、核销记录、退货记录 轻度重置范围 + 系统配置表：角色、权限、菜单、字典、用户、组织架构、流程定义、文件存储 —
Flowable清理 清理 ACT_RU_*（运行时）+ ACT_HI_*（历史） 清理全部 ACT_* 表，重新部署流程定义 —
文件清理 清理业务上传文件（银行回单、发票文件） 清空文件存储目录 —
保留内容 系统配置（角色、权限、菜单、字典、流程定义、管理员账号） 仅保留建表 DDL，重新执行初始化向导 —
适用场景 试运行期间业务数据乱了，想重新测 彻底重来，恢复出厂设置 试运行期间
上线后 禁止 — trial_mode = false 后重置接口返回 403，按钮不可见
